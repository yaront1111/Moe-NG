QA's drill found TWO surviving mutations inside `sameHold`, the one guard implementing DoD 1's
exact-hold clause: cutting `HOLD_IDENTITY_KEYS` from 10 keys to `["holdId"]`, and deleting both
`workerHandoff.digest`/`.ref` comparisons, each left the whole suite green.

Root cause was NOT the production code — `sameHold` was correct. All three `MALFORMED_HOLDS`
variants are SCHEMA-invalid (`lifecycle "RELEASED"`, `"not-a-proposal-base-hash"`, `graphEpoch -1`),
so `validExpansionProposeCommand` refused first and `sameHold` was never reached. The only test that
reached it varied `holdId` alone. See `mem:gotcha-identity-match-guard-shadowed-by-schema-layer`.

Fix — TESTS ONLY, zero production bytes changed this round:
- `CHANGED_HOLDS` in `planning-run-test-fixtures.ts`: 10 WELL-FORMED single-field deviations, one
  per compared field, incl. both `workerHandoff` fields. `lifecycle`/`truthClass` are excluded and
  documented — both are pinned constants, so no well-formed deviation exists.
- The mismatched-hold case became a sweep that asserts, per case: the exact field-NAME set
  (`toEqual`, whole set — not a count), `validExpansionHoldBinding(deviation) === true` against the
  PRODUCTION predicate, that the entry deviates at the field its key NAMES, then
  `expectIllegal(..., "plan.propose", "PLANNING")`.
- New `planning-run-expansion-cancel.test.ts` (106 lines) for DoD 4's competing finalize/cancel
  schedules on an EXPANSION run.

The expected field set is HAND-WRITTEN and deliberately NOT derived from `HOLD_IDENTITY_KEYS`. A
sweep generated from the production constant shrinks silently when a key is dropped from it, and
the D1 drill could then never redden. See `mem:qa-generated-table-cannot-police-its-own-generator`.
