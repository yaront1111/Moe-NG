# Backup generation: WAL pinning and atomic publish

For a restorable SQLite backup at an exact committed event cursor, do not copy the live main database or its WAL/SHM files. Use a dedicated read-only `node:sqlite` connection, `BEGIN DEFERRED`, validate project/schema, read the tail cursor to establish the WAL snapshot, require it equals the requested cursor, and await `backup(reader, stagedPath)` before committing. Reopen and validate the produced database and exact cursor before hashing.

Snapshot all caller-owned descriptor/RPO/key data synchronously before the first await; reject hostile/mutable shapes. Stream-copy and fsync payloads into an exclusive same-parent staging directory, build/sign the deterministic manifest only after all bytes verify, verify staging through the production verifier, atomically rename the whole generation, persist the rename cross-platform, and reverify exact final inventory. Keep signature outside the canonical digest-bearing manifest and require an external trusted key/chain anchor. Any missing, mismatched, concurrent, crypto, IO, persistence, or cleanup uncertainty must expose no restorable manifest and remain UNKNOWN with stable code and layer.
