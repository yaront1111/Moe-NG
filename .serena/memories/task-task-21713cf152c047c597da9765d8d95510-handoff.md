## Design consequences worth knowing before you build on this

- A valid proof BURNS its replay digest before core's later GENERATION/SESSION_STATE/EXPIRY/
  TRANSPORT refusals — core's precedence is BINDING, PROOF, REPLAY, then the rest. So a refused
  authentication can still append one replay event. Tests correctly assert the *session* aggregate
  is unchanged, not the global event count. Don't "fix" this by counting all events.
- Consequently `renewSession`/`rotateCredential`/`closeSession` are NOT replay-idempotent on an
  identical retry: `authorize` authenticates first, the nonce is already burned, and the retry
  refuses SESSION_REPLAYED/REPLAY before ever reaching the command-decision replay. A retry needs a
  fresh nonce. Only `createPrincipal`/`openSession` return the stored receipt on a true replay.
- `rotateCredential` verifies the NEXT key's signature after `authorize`, so a bad next signature
  returns AUTHENTICATION_FAILED/PROOF with the nonce already spent.
- Authenticating with a superseded credential id reaches core's GENERATION layer rather than
  BINDING, because `authenticate` rebuilds the session with the *held* credential's clientKeyId
  (session-authority.ts:216). See `gotcha-core-session-generation-layer-binding`.
