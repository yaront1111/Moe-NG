## Decisions the settlement sibling (17.04/17.05) must know

- **The plan's signatures were wrong and I changed them.** `cancelReservation` needs the VIEW to
  refund into — a pure function cannot restore buckets without it, and the DoD demands the refund
  restore the view. `activateReservation` takes the view too and returns **the same reference**,
  which turns "activation moves no units" into a `toBe` assertion instead of a weaker deep-equal.
- **`BudgetAvailableView` is a NARROW projection**, not `BudgetAccountRecord`:
  `{accountId, state, version, meters}`. 17.05 projects it from a ledger account in one line.
  Reserving bumps `view.version` by 1 (both reserve and refund), matching the ledger convention
  that every movement bumps the account version.
- **Activation moves NO units.** It is a one-use marker binding `attemptRef`.
  RESERVED -> COMMITTED (design 602) is settlement's job and is deliberately absent here.
- **Issue messages are DERIVED from the code** (`code.slice("BUDGET_RESERVATION_".length)`
  lowercased, underscores to spaces). This was the compaction that fit 18 codes and ~20 guard rows
  under the hard 249-line cap without dropping a guard, and it makes prose drift impossible.
  Do not "improve" it back into hand-written strings — the file has no room.
- **Guards are an ordered `Check` table**, `type Check = readonly [boolean, code]` plus
  `firstOf()`. First failing check decides the SINGLE reported code. This is both the size win and
  the readable statement of the precedence the DoD demands.

## The concurrency subtlety that cost me a test

**With pure functions and no registry, two competitors holding the same version-0 record BOTH
succeed.** One-use is only observable when the loser is applied to the successor the winner
produced. My first test passed the pre-activation record and caught the loser succeeding — which
was the test being wrong, not the code. Fixed test applies the loser to `winner.reservation` with
its stale `expectedVersion: 0` and gets `STALE_VERSION`.

Consequence for 17.05 and persistence: **this module supplies the compare-and-swap fence; the
store must enforce at-most-one.** Likewise a caller passing the already-shifted view with its
matching expectedVersion can reserve the same `admissionRef` twice and mint the same
`reservationId` twice. That is why the identity is deterministic and length-prefixed
(`reservation:<len>:<accountId>:<admissionRef>`) — the store inserts on it and rejects the second.

## Known limitations, stated not hidden

1. At-most-one reservation per admission is NOT enforced here (persistence, out of scope).
2. `fail()` deep-freezes the result, which holds the caller's view by reference, so a refusal
   freezes the caller's view object. Landed sibling behaviour, deliberate, but it is a side
   effect on a refusal path.
3. Gate is checked last by pinned precedence, so an unauthorized caller with a shortfall learns
   `INSUFFICIENT_AVAILABLE` before being refused for authority.
4. An empty `amounts` array refuses `MALFORMED`, not `PROTECTED_PURPOSE_MISSING`.
