# Product workspace delivery policy audit

Date: 2026-09-13. Source inspected at shared HEAD `8b80d247e2408c20333362d9d34ea3302540b2eb`, with the current task's preview-source changes uncommitted. This is a scoped implementation finding, not evidence of deployment or external product acceptance.

## Policy to preserve

Release currently depends on machine evidence. An absent or rejected preview does not prohibit release. The source explicitly records the owner's 2026-09-09 direction to approve the plan at the start and rejects adding a mandatory preview-approval prerequisite: [release-decide-service.test.ts](../../apps/daemon/src/release/release-decide-service.test.ts#L437), [gates-compose-journey.test.ts](../../apps/daemon/src/gates-compose-journey.test.ts#L14). The refactor must preserve that behavior rather than turn the earlier engineering proposal's unaccepted gate ideas into policy.

Deployment likewise records an exact release citation when available and explicitly records its absence. It does not refuse solely because a release is missing: [deploy-service.ts](../../apps/daemon/src/deployment/deploy-service.ts#L234), [deploy-ports.ts](../../apps/daemon/src/deployment/deploy-ports.ts#L47).

The inspected contracts contain no dedicated selector for products requiring preview approval before release, or release before deployment. Policy action/tier opt-ins decide whether an existing decision may run automatically; they do not establish a mandatory preview-to-release dependency: [policy-contract.ts](../../packages/core/src/policy/policy-contract.ts#L90), [release-auto-approval.ts](../../apps/daemon/src/release/release-auto-approval.ts#L160). Product deployment requirements carry prose and optional environment-variable names: [product-contract-v2-contract.ts](../../packages/core/src/product-contract/product-contract-v2-contract.ts#L110). Recognized `preview command`, `preview port`, and journey `preview path` directives configure execution; their presence does not authorize treating preview approval as a mandatory release gate: [preview-command-resolution.ts](../../apps/daemon/src/preview/preview-command-resolution.ts#L21).

No release/deployment authority change is justified by these sources. CLI products and products without previews retain their existing delivery paths. Configured operator fences, paired-human release admission, policy opt-ins, and durable command reconciliation remain authoritative.

## Existing exact bindings and presentation limits

- Deployment's command adapter already resolves a release receipt by admitted project, goal, requested SHA, and `RELEASED` outcome. An absent receipt remains absent; an invalid receipt refuses with its existing code before deployment effects: [deploy-command.ts](../../apps/daemon/src/deployment/deploy-command.ts#L334). This is an existing binding, not an unimplemented gate.
- Release checks criterion evidence against the requested SHA, then reads that goal/SHA's stored dossier before publisher and PR effects: [release-decide-service.ts](../../apps/daemon/src/release/release-decide-service.ts#L155). The preview verdict is supporting context rather than an admission prerequisite.
- The dossier's preview projection is goal-scoped and follows the latest durable decision, but its public fact shape omits SHA and preview receipt identity: [release-durable-facts.ts](../../apps/daemon/src/release/release-durable-facts.ts#L74), [release-dossier-contracts.ts](../../apps/daemon/src/release/release-dossier-contracts.ts#L92). The rendered section therefore does not establish that this preview applies to the released SHA: [release-dossier-sections.ts](../../apps/daemon/src/release/release-dossier-sections.ts#L141). The workspace must not infer exact candidate acceptance from that section.

A future attribution improvement can add the preview SHA/receipt identity to the dossier facts and label historical or unmatched context explicitly. Its meaningful red cases are preview A shown beside release B, an unreadable latest decision following an older approval, and a matching decision/receipt positive control. This can improve evidence attribution without changing the release admission policy. It would own the four dossier files cited above, their focused tests/fixtures, and any explicitly authorized wire readers; it is not implemented by this audit.

## Preview-source prerequisite implemented in this task

New preview starts extract the requested commit through the existing isolated bare Git source reader and compare materialized files to their raw Git blob hashes. Command selection and process cwd use that extraction; captures stay under the configured project directory. Dirty repository bytes and later HEAD/worktree changes do not alter the selected starting source: [preview-source.ts](../../apps/daemon/src/preview/preview-source.ts), [preview-runner.ts](../../apps/daemon/src/preview/preview-runner.ts#L162).

Missing or unmeasurable commits, repository-subdirectory ambiguity, symlinks, submodules, and checkout-transformed bytes refuse as `PREVIEW_GOAL_NOT_LANDED @ GOAL_AUTHORITY` before product process/capture. The source is retained while the process runs and reclaimed after measured exit, including startup, capture and receipt-write failures. Windows can retain an OS process row after a stop attempt; completed attempts that still observe a live process may be retried, and source cleanup waits for exit. This does not create a new approval or release prerequisite.

The authorized default preparation restores ordinary Node package-script previews without attaching mutable workspace `node_modules` or ignored build output. When the committed manifest declares dependencies or workspaces, npm uses `ci` with lifecycle scripts disabled, or pnpm uses frozen-lockfile installation with lifecycle scripts disabled. The package-manager choice must agree with the one committed lockfile family and any `packageManager` declaration. Missing or ambiguous lockfiles refuse as `PREVIEW_COMMAND_MISSING @ RUNNER`. If the selected fallback is `preview` and the committed manifest defines `build`, that build runs first; `dev` and `start` do not acquire a build step. Explicit injected contract commands retain their existing execution semantics and preparation responsibility. See [preview-runtime.ts](../../apps/daemon/src/preview/preview-runtime.ts).

Preparation runs inside the extracted tree, with the preview's existing runtime environment allowlist and explicitly delivered variables. Its output is discarded and each command has a bounded timeout and tree-stop path: [preview-preparation-process.ts](../../apps/daemon/src/preview/preview-preparation-process.ts). Tracked bytes and directory containment are measured again after preparation, after readiness before capture, and after capture before a `STARTED` receipt. An install/build failure or observed source drift refuses as `PREVIEW_START_TIMEOUT @ RUNNER`; generated untracked build output is permitted. Offline local-package integration tests cover npm and pnpm installation, build, disabled lifecycle scripts, dirty original-source preservation and refusal cutoffs.

Default installation checks committed manifests, lockfiles and workspace definitions for local dependency paths before installer effects. JSON and structured YAML parsing resolve pnpm links relative to their importer, reject escaped or absolute local inputs, and reject ambiguous YAML aliases. Installed dependency links are then checked for containment inside the extracted tree. Pnpm config hooks are explicitly disabled, and command arguments keep its modules, virtual store and cache directories inside the extraction even when committed config names external directories. The daemon adds a direct dependency on the already locked `yaml@2.9.0` parser. See [preview-dependency-boundary.ts](../../apps/daemon/src/preview/preview-dependency-boundary.ts).

The guarantee concerns measured source bytes and the owned listener. Configured commands can generate files or consume external inputs; locked network dependencies are not a hermetic runtime sandbox, and continuous tamper-proof execution is not claimed. Historical V1 receipts gain no retrospective source proof, and screenshot records still name paths without content digests.

The production V2 command registry now receives the same preview supervisor, workspace and decision port as V1. Executable directives from the latest approved V2 contract are deliberately **not** newly composed: a goal-bound current contract does not prove applicability to an older requested SHA. The existing [compiled-contract-binding.ts](../../apps/daemon/src/planning/compiled-contract-binding.ts#L55) reader validates V1 revisions, and [daemon-v2-command-registry.ts](../../apps/daemon/src/daemon-v2-command-registry.ts) still withholds V2 decomposition submission. An exact V2 candidate-to-contract binding is required before production can safely use those directives. This preserves committed package-script execution without inventing a new global gate or substituting newer contract prose for historical candidate authority.
